# 既知の問題・制約・技術的負債

## 状態ラベル

- **確認済み**: 現在のコード、テスト、または再現結果から事実として確認できる。
- **要再確認**: 過去の監査・コード上の懸念はあるが、現在のブラウザや対象環境での再現をまだ確認していない。
- **要件差分候補**: 現在の実装と正式要件の差として、実装要否を判断する必要がある。
- **未評価**: 実機、出力、性能、公開など、この調査で測定していない。

## 現在の項目

### SVG／Safari互換性 — 未評価

過去のUX監査では、SVGのpresentation attributeへCSSカスタムプロパティを渡す実装が、古いSafariや一部のSVG処理系で期待どおり解釈されない可能性を指摘している。2026-08-19のソース調査では、`src/core/export.ts`の`fill-opacity`は直接値を出しており、同じ実装が現在も残ることは確認していない。ただしiPad SafariとPNG/PDF出力の実物確認は未実施なので、互換性の受入は未評価として残す。

### iPad／タッチ／表示 — 未評価

この調査では開発サーバーを対象ブラウザやiPadで操作していない。Pointer Events、2本指パン・ピンチ、パネルのレスポンシブ表示、フォーカス、画面リサイズ、スクリーンリーダーは、対象環境での受入が別途必要である。

### 出力精度・大規模性能 — 未評価

印刷・PNG・PDFの目視、実寸縮尺、寸法精度、複数ページ、500オブジェクト規模の操作性能は未測定である。ビルドの大きなチャンク警告（PDF.js／Three.js）も初回ロード性能の評価課題として残る。

### 埋め込み背景と保存容量 — 要再確認

画像やPDFページをdata URLとしてProjectへ埋め込むため、JSON・自動保存が大きくなる可能性がある。IndexedDBとlocalStorageフォールバックの容量上限、巨大PDF、複数背景での挙動は定量評価していない。

### クライアント側ベータゲート — 確認済みの制約

`VITE_BETA_PASSWORD`を使うベータゲートはクライアント側のUI制御であり、秘密情報や強固な認証の代わりではない。公開時のアクセス制御はGitHub Pages／Cloudflare等の運用境界で別途検証する。パスワードをProjectデータとして扱ったり、通常のアプリデータを外部へ送信する設計へ変更したりしない。

### 保存層の後方互換shim — 確認済みの技術的負債

`src/core/storage.ts`は純粋core実装ではなく、`src/services/web/indexedDbStorage.ts`を再exportする旧import互換のshimである。さらに現行の`WebAutosaveService`もこのshim経由でWeb実装を参照している。動作上の不具合は確認していないが、`core/`をブラウザ非依存とみなす際の例外である。新規コードは`AutosaveService`または`src/services/web/`の正規実装を使い、shimへ依存する箇所を増やさない。

### 表示変更だけでは自動保存しない — 確認済みの挙動

`Project.view`はJSONへ保存される一方、`SET_VIEW`はUndo履歴や`saveState: dirty`を更新しない。このためズーム・パンだけを変更して終了した場合、その表示状態だけを目的とした自動保存は起動しない。その後の確定編集や明示保存では、その時点のviewも保存される。これを不具合として変更する場合は、編集履歴へ含めるか、自動保存だけを起動するかを先に決める。

### UI自動受入の不在 — 確認済みの技術的負債

現在の自動テストはNode環境の`*.test.ts`だけで、DOM、Playwright、スクリーンショット差分、iPad Safariを自動評価しない。未コミットのUI差分を含め、表示・フォーカス・Pointer Events・アクセシビリティの回帰はブラウザ／実機確認が必要である。

## 要件差分候補

現行コードからは次の要求を完全に満たす機能が確認できない。実装前に要件番号と受入条件を再確認する。

- 任意角度の背景回転（FR-015）
- X/Y別の校正（FR-025）
- 一般的な原点設定（FR-032）
- ユーザー向けの前面／背面操作（FR-054相当。内部の`zIndex`とは別）
- 全オブジェクトを対象にした重複・舞台外・クリアランス警告（FR-090〜FR-092相当）
- 明示的なプロジェクト複製操作（FR-004相当）
- UI文字列を将来の多言語化向けに分離する構造（NFR-014後半。現状は各コンポーネントへ日本語文字列が直接記述されている）

ここに挙げたものは今回の文書整備で修正していない。実装する場合は、mm正本、Action、保存互換性、単体テスト、実機受入までを1つの契約として設計する。

## 回避と更新

- 未確認の互換性・実機・出力問題は、手動確認が済むまで受入済みと表示しない。
- 要件差分を実装するときは、先に`current-state.md`の候補を作業契約へ移し、完了後にコード・テスト・受入結果を更新する。
- 問題が解消されたと判断した場合は、再現条件、確認環境、確認日を記録してから状態を変更する。
