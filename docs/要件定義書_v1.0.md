# 1. 背景・目的

> **最重要設計原則**
> 背景画像上のピクセル座標を正本にしない。背景画像を実寸座標系へ校正し、すべての配置物はmm単位の座標・寸法・角度を正本として保持する。画面ズームや画像解像度が変わっても実寸値は変化しないこと。

多くのホールは舞台平面図をPDFまたは画像で公開している。一方、実際の演奏会準備では、印刷した図面への手書き、画像編集ソフト上での記号配置などが行われ、縮尺の一貫性、修正容易性、再利用性に課題がある。

本システムは、ホール舞台図面を背景として読み込み、既知距離から縮尺を校正し、椅子・譜面台・大型楽器・舞台設備等を実寸ベースで配置できる編集環境を提供する。出力されたPDFはホールの舞台スタッフへの提出図面として通用する縮尺精度を持つ。

## 1.1 前提知識(日本のホール図面)

- 日本のホール平面図は尺貫法ベースのグリッドで描かれているのが通例。1マスは3尺(910mm)または1間(1820mm)が多い。
- ただし余白・向き・注記量・グリッド間隔はホールごとに異なるため、特定のマス数を前提とせず、任意の既知距離で校正できる方式を必須とする。校正距離の入力にはプリセット(910/1820mm等)を提供し、日本のホール図面での入力を高速化する。
- 多くのホールは反響板設置状態の平面図を公開しており、反響板の側板・後板の位置が図面上に読み取れる(Phase 5の3D化で使用)。

## 1.2 解決する課題

- 図面ごとに画像解像度や余白が異なり、単純な流用では寸法が揃わない。
- 椅子や楽器を手作業で描くとサイズが不統一になり、舞台に収まるか判断しにくい。
- 多数の椅子・譜面台を1個ずつ配置する作業負荷が高い。
- 修正前後の版管理や、別公演・別ホールへの再利用が難しい。
- 提出時に操作ハンドルや補助線が残るなど、出力品質が安定しない。
- 山台の段高や視線(サイトライン)の妥当性を事前に確認する手段がない。

## 1.3 成功状態

- 任意のホール図面を読み込み、既知距離を指定して実寸座標系を設定できる。
- 椅子・譜面台等を標準寸法で配置し、拡大表示しても実寸が変わらない。
- 配置図を保存・再編集でき、印刷縮尺の正確なPDFとして提出できる。
- iPadのみで取り込み→校正→配置→出力の一連の作業が完結する。
- (Phase 5)配置を一人称3Dで確認し、奏者席からのサイトラインを検証できる。

# 2. 適用範囲

## 2.1 MVP(Phase 0〜3)に含む範囲

- PNG・JPEG・PDFの舞台図面読み込み
- 背景図面の回転、切り抜き、位置調整、透明度変更、ロック
- 2点間の既知距離による縮尺校正(距離プリセット付き)
- mm単位でのオブジェクト配置・移動・回転・複製・削除
- 椅子、譜面台、指揮台、山台、基本図形等のプリセット
- 複数選択、整列、等間隔配置、グループ化、Undo/Redo
- ローカル保存、プロジェクトファイル入出力
- 印刷縮尺(1:50/1:100)を保証したPDF出力、PNG出力
- 距離測定、オブジェクト寸法・座標表示
- PC(マウス)とiPad Safari(タッチ)の両操作系

## 2.2 MVPに含めない範囲

- 複数ユーザーによるリアルタイム共同編集
- クラウドアカウント・課金・権限管理
- 画像からの椅子・楽器・手書き記号の自動認識
- 写真撮影された図面の台形・遠近補正
- DXF/DWG等のCADファイル互換
- 照明・吊物・音響回線の専門CAD機能
- 楽器メーカー・機種ごとの完全な外形データベース
- 3D一人称ビュー(Phase 5として本書第8章に要件を定義済み)

# 5. システム概要

> **前提条件**
> MVPでは、PDFから直接取得した図面または縦横比が維持された画像を主対象とする。スクリーンショットは利用可能だが、縦横比が変形していないことを前提とする。

## 5.1 論理構成

| 構成要素 | 責務 |
|---|---|
| Background | 元画像/PDFページ、切り抜き、回転、表示位置、透明度、ロック状態を保持する。 |
| Calibration | 校正基準点、入力実距離、mmPerPixel、原点、校正日時を保持する。 |
| Scene | mm単位でオブジェクト・壁を保持し、選択・描画・整列・スナップを行う。 |
| Object Library | プリセットの種類、標準寸法(W/D/H)、形状、ラベル初期値を提供する。 |
| Project Storage | 自動保存、名前付き保存、JSON入出力、スキーマバージョン管理を行う。 |
| Exporter | PNG/PDF用に背景・オブジェクト・注釈を実寸基準で再描画する。編集ハンドルは出力しない。印刷縮尺を管理する。 |
| Viewer3D(Phase 5) | Sceneデータから3Dシーンを生成し、一人称/客席/俯瞰カメラを提供する。遅延読み込み。 |

## 5.2 基本ワークフロー

1. 新規プロジェクトを作成する。
2. ホール図面を読み込み、対象ページを選択する。
3. 回転・切り抜き・背景位置を調整する。
4. 図面上の2点を選び、実距離を入力(プリセット選択可)して校正する。
5. 測定ツールで校正結果を確認する。
6. ライブラリからオブジェクトを配置し、座標・角度・ラベルを調整する。
7. 整列、等間隔、グループ化等で配置を整える。
8. 保存し、PNGまたは縮尺指定PDFとして出力する。

## 6.1 縮尺校正の詳細要件

- 校正モード開始時、ユーザーは背景図面上で始点・終点を指定する。タッチ操作時は拡大表示と組み合わせて精密に打点できること。
- 入力値は正数のみとし、0または負数、未入力は確定不可とする。
- 内部値は mmPerPixel として保持する。MVPでは等方スケール(X=Y)を前提とする。
- 背景画像の画面表示倍率を変更しても、校正結果と実寸座標は変化しない。
- 校正済みでない状態では、実寸オブジェクト配置を禁止するか、未校正警告を常時表示する。
- 再校正時は、既存オブジェクトの実寸座標・寸法を維持し、背景との相対表示のみ再計算する。

## 6.2 オブジェクト寸法の詳細要件

- プリセットの寸法は初期値であり、実際の備品・楽器に合わせて数値変更できる。
- オブジェクトの正本は xMm、yMm、widthMm、depthMm、heightMm、rotationDeg とする。
- 回転時に widthMm、depthMm を入れ替えない。回転は描画変換として扱う。
- 画面上の見た目だけを拡大縮小するズームと、物体寸法の変更を明確に分離する。
- ラベルはオブジェクトと一体で移動するが、表示/非表示を切り替えられる。
- heightMmは2D描画では使用しないが、Phase 0のスキーマ定義時点から必須フィールドとして持つ(プリセット既定値を適用)。

## 6.3 保存・互換性の詳細要件

- プロジェクトデータには schemaVersion を必須とする。
- 背景画像はプロジェクトファイル内にBase64で埋め込む(単一ファイル化を優先)。容量増加は性能検証する。
- 読み込み時に未知のフィールドは無視し、既知フィールドを復元できる設計とする。
- 自動保存は最終操作から1〜3秒後にデバウンスして実行する。
- 保存失敗時は明確なエラーを表示し、未保存状態を識別できるようにする。
- walls(壁トレース)フィールドをPhase 0からスキーマに予約する(空配列可)。

# 8. Phase 5: 3D一人称ビュー要件

2D配置データを立体化し、奏者・指揮者・客席の各視点から配置を検証する機能。**2Dデータ構造の拡張のみで実装し、2D機能に破壊的変更を加えないこと。**

## 8.1 壁トレース(反響板の入力)

- 2D画面上に「壁トレースモード」を設け、背景図面の反響板・壁のラインをクリック/タップでなぞって折れ線(ポリライン)を入力できる。
- 曲面の反響板は折れ線の細かい打点で近似する。頂点の追加・移動・削除が可能。
- 各ポリラインに高さを設定できる(既定6000mm)。
- 壁データはプロジェクトJSONに保存される。
- 天井反響板は対象外(平面図から傾斜が読めないため)。省略または任意高さの水平板で近似するオプションのみ提供。

## 8.2 3Dシーン生成

- 2Dデータ(オブジェクト・壁・山台)から3Dシーンを自動生成する。専用のモデリング作業は不要。
- 床: 校正済み背景図面をテクスチャとして貼る/不透明度調整/無地+実寸グリッド、の3モード切替。
- 壁: トレースしたポリラインを指定高さで押し出す。
- オブジェクト: 平面形状をheightMmで押し出したプリミティブ(箱・円柱)で表現する。精密な3Dモデル(glTF)は不要。
- 山台: 段高どおりの箱として生成し、山台に関連付いたオブジェクト(FR-063)はその天面から積み上げる。
- 簡易奏者アバター: 椅子オブジェクトの位置に、座奏者を模した簡易形状(円柱+球、頭頂約1200mm)を表示できる(ON/OFF可)。立奏・コントラバス等は1600〜1700mm。サイトライン検証ではアバターを最優先の表現とする。
- 舞台前端の外側に客席方向の床面を延長し、客席側からの視点確認に使えるようにする。

## 8.3 カメラと視点

- 一人称視点: 任意の位置に視点を置き、目線高さをプリセット(座奏1200mm/立奏1600mm/指揮者1700mm/任意値)から選択。
- ミニマップまたは2D画面上でタップした位置に視点を移動できる。
- 椅子オブジェクトを選択して「この席から見る」で即座にその奏者視点へ切り替えられる。山台上の椅子は段高分視点が上がる。
- 客席視点: 舞台正面の任意距離・高さからのプリセット。
- 俯瞰視点: シーン全体のオービットカメラ。

## 8.4 操作系

- PC: マウスドラッグまたはPointer Lockによる視点回転 + WASD/矢印キー移動。
- iPad/タッチ: 片指ドラッグで視点回転 + タップ位置へ移動(またはバーチャルスティック)。Pointer Lock APIはiOS Safariで使用不可のため、タッチ用操作系は自前実装とする。
- 3Dビューは閲覧専用とし、編集は2Dに戻って行う。2D/3Dはワンタップで相互切替。

## 8.5 3Dの非機能要件

- オブジェクト200個+アバター100体+壁で、iPad Safari上30fps以上を目標とする(ジオメトリのマージ・インスタンシングを活用)。
- 3Dモジュール(Three.js)は遅延読み込みとし、2D側の初期表示速度に影響を与えないこと。

## 9.4 座標変換の原則

- SceneObjectの位置と寸法は常にmmで保存する。
- 画面描画時のみ、校正情報とビュー変換からpxへ変換する。
- ポインター/タッチ操作で得たpx座標は、直ちにmmへ逆変換して保存する。
- ズーム、パン、端末ピクセル比はプロジェクトの実寸データへ影響させない。
- 背景の切り抜き・回転・校正の順序を固定し、変換行列として一元管理する。
- Phase 5の3D空間は同一のmm座標を写像する(単位換算と軸の扱いのみ)。2D/3Dでデータを二重管理しない。

# 12. 推奨技術構成

> **位置づけ**
> 本章は実装方式の推奨であり、機能要件そのものではない。Codexが別案を採用する場合も、実寸座標の一貫性、保存互換性、テスト可能性を満たすこと。

| 領域 | 推奨 |
|---|---|
| 言語 | TypeScript(strict有効) |
| UI | React + Vite |
| 描画(2D) | SVGを第一候補。500個配置の性能試験で不足すればCanvas/Konva等を検討。 |
| 描画(3D) | Three.js。動的import による遅延読み込み。 |
| PDF入力 | PDF.js |
| PDF出力 | ベクトル再描画可能なPDFライブラリ(pdf-lib等)。背景は画像埋込みでも可。mm→ポイント換算を厳密に管理。 |
| ローカル保存 | IndexedDB。設定のみlocalStorageを使用可。 |
| 状態管理 | 小規模ならReact state + reducer、複雑化時はZustand等。 |
| テスト | Vitest + Testing Library。E2EはPlaywright推奨(タッチイベントのエミュレーション含む)。 |
| 型検証 | Zod等でプロジェクトファイル読み込み時に検証。 |
| 配信 | 静的ビルド。GitHub Pages / Cloudflare Pages。 |

## 12.1 実装上の制約

- Canvas/SVG上のpx値を直接保存しない。
- 描画ライブラリ固有のオブジェクトをプロジェクトJSONへ直接保存しない。
- 座標変換ロジックをUIコンポーネントへ散在させず、純粋関数として分離する。
- Undo/Redo対象操作をコマンドまたは状態差分として統一する。
- 出力は画面スクリーンショットではなく、プロジェクトデータから再描画する。
- 機能追加前にスキーマ変更とマイグレーション方針を定義する。保存形式の破壊的変更は禁止し、schemaVersionとマイグレーションで対応する。
- ポインターイベントはPointer Events APIで統一実装し、マウス/タッチの分岐を最小化する。

## 付録A.1 プリセット設計原則

- 寸法の根拠が確認できない値を「正確な実寸」と表示しない。
- プリセット名に「標準」「大型」「任意寸法」等を明示する。
- ユーザーが寸法を変更した場合、元プリセット値とカスタム値を区別する。
- メーカー・機種別寸法は、公式仕様を確認できたものだけ追加する。
- 形状が複雑でも、配置検討に必要な精度を超える過剰なポリゴンを避ける。

# 付録B. 参考図面から導かれる要件

要件検討時に想定した入力は、(1)ホール公開図面に配置案を手書きした例、(2)マス目と吊物設備情報を含む舞台平面図の例である。公開図面は余白、向き、注記量、グリッド間隔がホールごとに異なるため、特定のマス数を前提とせず、ユーザーが任意の既知距離を指定して校正できる方式を必須とする。同時に、日本のホール図面では910/1820mmが支配的なため、距離プリセット(FR-021)により入力を高速化する。
