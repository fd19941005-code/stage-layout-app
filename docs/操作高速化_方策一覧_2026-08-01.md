## 2. 体感速度を落としている点

### 2-1. パネル操作直後に矢印キー・Deleteが効かない

`blocksCanvasShortcut()` は、フォーカスがボタン等のインタラクティブ要素にある間、`delete` と矢印を無効化する（`src/core/keyboardShortcuts.ts:96`）。
そのため「プロパティの＋15度ボタンを押す → そのまま矢印で寄せる」ができず、毎回キャンバスをクリックし直すことになる。クリックし直すと選択が変わる場合もある。

- なぜ問題か: 同じ操作が文脈によって効いたり効かなかったりする（[[Keyboard]] 予測可能性）。
- 直し方: パネル側のコマンド実行後にキャンバスへフォーカスを戻す。`blocksCanvasShortcut` のロジック自体は誤爆防止として妥当なので変えない。

### 2-2. モード切替にキーがない

12モードすべてがツールバーのボタン専用。距離を測る→選択へ戻る、のような往復が多い作業でマウス移動が積み上がる。

### 2-3. 配置のたびにライブラリへ戻る

同じ椅子を離れた場所へ何度も置く、椅子と譜面台を交互に置く、といった操作でカーソルがライブラリとキャンバスを往復する。連続配置は「同一プリセットの繰り返し」しか短縮しない。

### 2-4. ホイールが無条件でズーム

`handleWheel` は `deltaY` の符号だけを見る（`CanvasStage.tsx:273`）。トラックパッドの2本指スクロールがすべてズームになり、ノートPCやiPad+トラックパッドではスクロールで意図せず縮尺が変わる。

### 2-5. 空白がないとパンできない

パンは「オブジェクトにも注釈にもガイドにも当たらない場所を左ドラッグ」でしか始まらず（`CanvasStage.tsx:711`）、`handlePointerDown` 冒頭で `e.button !== 0` を捨てているため中ボタンも使えない。配置が密になるほどパンの開始点が減る。

## 3. 方策

### 第1層: 既存Actionへキーを割り当てるだけ（低コスト）

| # | 方策 | 割当案 | 使う既存Action / 関数 |
|---|---|---|---|
| 1-1 | モード切替のワンキー | `V`選択 / `B`範囲選択 / `M`距離を測る / `W`壁トレース / `K`縮尺合わせ / `P`指定点へ向ける | `SET_MODE` |
| 1-2 | 注釈モードのワンキー | `T`文字 / `L`線 / `A`矢印 / `R`矩形 / `O`円 / `N`寸法 | `SET_MODE` |
| 1-3 | 回転のキー操作 | `]`+15度 / `[`-15度 / `Shift+]` `Shift+[` は±5度 | `ROTATE_SELECTED_DELTA` |
| 1-4 | ズームのキー操作 | `Ctrl+0`全体表示 / `Ctrl+1`100% / `Ctrl++` `Ctrl+-` | `fitViewToProject` / `zoomAt` |
| 1-5 | 直前プリセットの再呼び出し | `Enter`（または `Q`） | `SET_PENDING_PRESET` + `libraryPreferences.recentPresetIds` |
| 1-6 | お気に入りプリセットの数字キー | `1`〜`9` | `SET_PENDING_PRESET` + `libraryPreferences.favoritePresetIds` |
| 1-7 | パネル操作後のフォーカス復帰 | — | キャンバスの `tabIndex={0}` 要素へ `focus()` |
| 1-8 | 選択の巡回 | `Tab` / `Shift+Tab` で次・前のオブジェクト | `SELECT` |

実装上の注意:

- 単キー割当は `getKeyboardShortcut()` へ追加する。テキスト入力中は `blocksCanvasShortcut()` が既に弾くので、入力欄との衝突は起きない。
- ただし 1-1〜1-6 は「フォーカスがボタンにあるとき」も動いてよい種類の操作なので、`blocksCanvasShortcut` の第2引数の分類（canvasFocusShortcut）に含めない判断が必要。
- 1-8 の `Tab` はブラウザ標準のフォーカス移動を奪う。キャンバスにフォーカスがあるときだけに限定し、パネルへ抜ける手段（`Escape`→`Tab`）を残す。
- `keyboardShortcuts.ts` は純粋関数なので、割当は単体テストで固定できる。

### 第2層: ポインタ操作の拡張（中コスト、`CanvasStage.tsx` 中心）

| # | 方策 | 内容 |
|---|---|---|
| 2-1 | 中ボタンドラッグでパン | `handlePointerDown` の `e.button !== 0` early return を、中ボタンならパン開始に分岐させる |
| 2-2 | スペース押下中のドラッグでパン | keydown/keyupで一時状態を持ち、カーソルを `grab` に変える |
| 2-3 | トラックパッド対応 | `wheel` の `e.ctrlKey`（ピンチジェスチャー）でズーム、素のスクロールはパン。従来のマウスホイール派のために設定で切替できるとなお良い |
| 2-4 | Alt+ドラッグで複製移動 | Ctrl+D→移動の2手を1手にする。ドロップ時に1回のcommitで履歴へ入れる |
| 2-5 | Alt押下中はスナップ一時無効 | `snapPoint()` の呼び出し側で修飾キーを見る。スナップパネルへ行かずに微妙な位置へ置ける |

注意: 2-4・2-5 はどちらもAltなので同時には使えない。2-5は `Ctrl`（macは `Cmd`）へ寄せるなど、割当は実装時に一度整理する。

### 第3層: 探す時間そのものを減らす（高コスト）

| # | 方策 | 内容 |
|---|---|---|
| 3-1 | コマンドパレット `Ctrl+K` | プリセット・一括配置ダイアログ・モード・レイヤー切替を1つの検索欄から実行。`filterLibraryPresets()` / `normalizeLibraryQuery()` を再利用できる。楽器プリセットは今後も増えるので、長期的にはこれが一番効く |

| 3-4 | 選択物にフィット | `Shift+F` 相当。多数配置後に対象へ寄る操作が現在は手動パン＋ズームになっている |

## 4. iPad併用時の扱い

キーボード施策（第1層・3-1・3-2）はタッチ単体では効果がない。iPadでの高速化は 3-3（コンテキストメニュー拡張）と 2-3（ピンチとスクロールの区別）が担当する。
第1層だけを実装するとPCとiPadの操作速度差が広がるため、iPadを主に使う運用なら 3-3 を先に入れる判断もありうる。

## 5. 実装順の目安

## 6. 適用した原則

`apple-hig-ui-ux` スキルの以下に対応する。

- [[Keyboard]]: 全操作にキーボード代替手段があること、同じ操作が文脈で変わらないこと（2-1・1-7）
- [[Toolbars]] / [[Menus]]: 頻用操作にショートカットを割り当て、かつメニュー等から発見可能にすること（3-2）
- [[Pointer Interaction]]: 入力デバイスごとの標準的な作法に従うこと（2-3のトラックパッド）
- [[Context Menus]]: ショートカットが使えない環境での代替経路（3-3）
- 精密配置ツール専用チェックリスト: キーボードでの微調整、ドロップ後の数値確認は既に満たしている。今回の提案はいずれもこれを損なわない
