# 文書体系

このディレクトリは、コードから復元しにくい設計理由、現在の状況、検証基準、既知の問題を、役割ごとに分けて管理する。各情報は1つのSource of Truthだけに置き、他の文書からは要約とリンクにとどめる。

## 新しいセッションの参照順

1. `../AGENTS.md`
2. `current-state.md`
3. `architecture.md` または `domain.md`
4. 変更内容に応じて `testing.md`、`known-issues.md`、`decisions/`
5. 要件番号を確認するときだけ `要件定義書_v1.0.md`

## Source of Truth

| 情報 | Source of Truth | 役割 |
| --- | --- | --- |
| 正式な要求・FR/NFR/AC | `要件定義書_v1.0.md` | 何を満たすべきかを定める |
| 機能別の詳細仕様 | `instrument-symbol-spec-final-v1.2.md`、`椅子多列円弧配置_仕様書_v1.1.md`、その他の版付き仕様書 | 要件を機能単位で詳述する。実装済みかどうかは `current-state.md` で判断する |
| システム構造・データフロー | `architecture.md` | どの層が何を担当するかを説明する |
| 用語・ドメイン制約 | `domain.md` | 実装時に壊してはいけない意味を説明する |
| 現在の実装状況 | `current-state.md` | 調査日時点で何が使え、何が未確認かを示す |
| テスト・受入評価 | `testing.md` | 自動検証と手動確認の方法・結果を示す |
| 既知の問題・制約 | `known-issues.md` | 回避策、未確認リスク、技術的負債を示す |
| 設計理由・過去の失敗 | `decisions/` | 現在の方法を採用した理由を記録する |
| 公開・運用手順 | `GITHUB_PUBLISH.md`、`.github/workflows/` | 外部状態を変更する手順。通常の開発検証とは分ける |
| エージェント向け恒久ルール | `../AGENTS.md` | 作業境界と不変条件の正本。`../CLAUDE.md`はClaude Code固有の読み替えだけを持つ |

コードは実装の正本であり、文書はコードを置き換えない。文書とコードが違う場合は、まず `current-state.md` の調査日と根拠ファイルを確認し、必要なら文書を更新する。正式な要求を変える場合は、要求変更として別途明示する。

## 履歴・参考資料の扱い

ルートの `HANDOFF.md`、`docs/UX監査_*.md`、旧アルゴリズムの仕様書、方策一覧、`codex-instrument-symbol-kickoff.md`や`操作高速化_実装依頼プロンプト.md`等の実装依頼プロンプトは、過去の検討・監査・作業経緯を残す資料である。削除せず、日付時点の記録として扱う。機能別の版付き仕様書は要求・設計の参照資料だが、実装状態のSource of Truthではない。いずれの場合も、次の情報を現在の事実として引用しない。

- その資料の調査日以降に変わり得る実装状況
- 「未実装」「受入済み」などの状態
- 旧アルゴリズムや旧UIの仕様

現在状態に影響する履歴は `decisions/` に理由として要約し、現在の検証可能な事実は `current-state.md` と `testing.md` に記録する。

## 更新ルール

- 実装変更後は、影響範囲に応じて `current-state.md`、`testing.md`、`known-issues.md` を更新する。
- 設計理由や失敗したアプローチが将来の変更判断に影響する場合は、`decisions/` に短いADRを追加する。
- 日付付き監査の追記で現在状態を上書きしない。監査結果を現状へ反映する場合は、根拠を再確認して現行文書へ移す。
- 文書整備のためにアプリ本体のコード、CSS、設定、依存関係を変更しない。必要なコード修正は別タスクに分ける。
